# V1：无支付核心流程

状态：业务范围已明确，以下验收尚未执行。更新：2026-11-17。
依据：2026-11-17“小程序制作讨论”中用户明确要求先推进商品浏览、商品管理、订单管理、订单确认，支付后续接入。架构采用共用小程序与微信云开发。

## 范围与流程
1. 经营者新增或编辑商品并上架。
2. 学生浏览在售商品，选择数量。
3. 学生进入确认页，核对商品与配送信息，填写必填手机号和可选备注。
4. 云端识别用户，检查商品与数量、营业规则，计算金额并保存订单快照。
5. 学生收到“订单已提交”结果；不调用支付、不模拟支付。
6. 经营者在订单列表与详情读取已提交订单，查看商品数量、手机号与备注。

开发顺序建议：商品管理 → 商品浏览 → 订单确认 → 订单管理。

## 原讨论记录的业务规则
以下来自原讨论的助手摘要，实施前应与经营者确认；不把摘要中未明确的细节补成新需求。
- 每日 14:00 截止下单。
- 17:00–17:30 统一配送至浙江财经大学学生生活区东门。
- 同一订单商品总份数 ≥ 2 免配送费；1 份收取 1–2 元，具体金额尚未确定。
- 手机号必填。
- 不做复杂库存、路线规划或配送批次选择。

待明确：单份配送费；14:00 整的边界和截止后是否仅提示停止当日下单。未确认前不自动把订单安排到次日。测试配置必须标注为测试值。

## 最小验收清单
以下是建议验收方式，不代表已通过。
- 经营者创建并上架商品后，学生可见；下架后不再允许新提交该商品。
- 学生能够核对商品数量、填写手机号与备注并提交，刷新经营者订单列表可见同一订单。
- 无手机号、非正整数数量、已下架商品不能生成有效订单。
- 客户端改价不能改变云端计算结果；商品编辑不改变已保存订单快照。
- 普通学生无法修改商品或读取其他学生订单；经营者可查看管理所需数据。
- 重试同次提交不会重复生成订单。
- 提交全程不依赖支付配置，页面不出现支付成功提示。
- 配送费与截止规则确认后，再按明确边界验证金额和时间条件。

## 明确排除
微信支付、支付回调、退款、模拟支付、复杂库存、路线与批次管理均不属于本次 V1。无支付流程用于先完成核心开发与验证；真实收款及上线安排另行确定。
